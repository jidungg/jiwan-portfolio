새 문제 해결 사례를 작성한다. 주제: $ARGUMENTS

## 절차

1. **소스 확인** — `Sources/Projects.md`·`Sources/Portfolios.md`와 관련 로컬
   저장소·GitHub·Notion을 확인한다. `Sources/Projects.md`의 우선순위(로컬이
   있으면 로컬, 없으면 GitHub)를 따른다. 관련 자료를 못 찾으면 사용자에게
   어디서 가져와야 하는지 먼저 묻는다.

2. **관련 이미지를 챙긴다** — `Sources/Portfolios.md`(기존 포트폴리오 PDF·Notion
   문서)에 이 사례와 관련된 스크린샷·그래프·다이어그램이 있으면 발견 즉시
   `Assets/<slug>_설명.png`로 받아 저장해둔다. Notion 이미지 URL은 몇 분 내
   만료되니 미루지 않는다.

3. **질문으로 캐낸다** — 아래 항목을 채울 만큼만 묻는다. **모든 항목을 억지로
   채우려고 하지 않는다** — 답할 만한 정보가 없으면 그 항목은 비워두고, 어디서
   확인해야 하는지 사용자에게 되묻는다.
   - 상황·제약 (왜 문제였고, 무엇이 어려웠는가)
   - **접근** — 검토했다가 버린 대안 최소 1개와 버린 이유. 이게 제일 중요하다.
     사용자가 "그냥 이렇게 했어요"라고만 답하면, "그 방법 말고 처음에 고려했다가
     안 쓴 방법 없었어요?"라고 다시 물어라.
   - 구현 핵심 (코드 20줄 이내로 압축 가능한 정도)
   - 결과 — **측정된 수치와 측정 조건(기기·씬·반복 횟수)만.** 어떻게
     측정했는지(테스트 코드, 임시로 바꿔본 방법 등)는 묻지도, 쓰지도 않는다.
   - 회고 — 지금 다시 하면 무엇을 바꿀 것인가

4. **id/slug을 정한다** — 영문 kebab-case. `Cases/<slug>.md`가 파일명이 된다.

5. **`Templates/case.md`를 복사해 채운다.**
   - frontmatter의 `id`는 slug와 반드시 일치시킨다. `status: draft`로 둔다.
   - **frontmatter에 metrics 필드를 만들지 않는다** — 숫자는 본문 '결과'
     섹션에만 적는다.
   - **본문은 '-습니다'체로, 동료에게 설명하듯 친절하게 쓴다.** 딱딱한
     보고서체(-다체)로 쓰지 않는다.
   - 채울 정보가 없는 항목은 비워두거나 "확인 필요: ___"로 표시한다. 빈 칸을
     메우려고 지어내지 않는다.

6. **소스에 없는 수치·기술을 지어내지 않는다.** 확인 안 된 값은 빈칸으로 두고
   사용자에게 묻는다. 이건 협상 대상이 아니다.

7. 작성 후 `python tools/build.py validate`를 실행해 형식 오류가 없는지 확인하고,
   `python tools/build.py index`로 `Cases/INDEX.md`를 갱신한다.

8. 다 쓴 뒤 사용자에게 알린다: 이 사례는 `draft` 상태이며, `/review-case <id>`를
   통과해야 빌드에 쓸 수 있다는 것을 상기시킨다.
