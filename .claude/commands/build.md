JD를 받아 포트폴리오를 조립한다. 인자로 JD가 안 왔으면 사용자에게 JD 원문을
붙여넣어 달라고 요청하고, 회사명·포지션·지원 마감일도 함께 물어본다.

## 절차

1. **JD 저장** — `Applications/<YYYY-MM-DD>-<회사>-<포지션>/jd.md`를 만들고
   JD 원문을 그대로 저장한다. 날짜는 오늘 날짜(빌드일)를 쓴다.

2. **JD 분해** — 자격요건 / 우대사항 / 주요업무로 나누고, 각 항목을 태그
   (`domain`, `skills`에 쓰이는 것과 같은 어휘)로 정규화한다.

3. **후보 추림** — `Cases/INDEX.md`에서 `status: ready`인 사례만 대상으로,
   frontmatter 태그가 JD 태그와 겹치는 것을 1차로 추린다.

4. **본문 판단** — 후보로 좁혀진 사례들의 본문을 읽고, 이 JD에 실제로
   설득력 있게 대응하는지, 어떤 순서로 배치할지 판단한다. 태그가 겹쳐도
   맥락이 안 맞으면 뺀다.

5. **선별안 제시 → 승인 대기** — 다음을 표로 제시하고 **사용자 승인 전에는
   진행하지 않는다**:
   - 고른 사례 목록과 순서
   - 각 사례를 고른 이유 (JD의 어느 항목에 대응하는지)
   - JD에서 요구했지만 대응할 사례가 없는 항목 (미충족 목록)
   사용자가 순서·구성을 바꾸자고 하면 반영하고 다시 확인받는다.

6. **manifest.yaml 작성** — 승인된 내용을 `Applications/<dir>/manifest.yaml`에
   기록한다. 스키마:
   ```yaml
   company: 회사명
   position: 포지션
   date: YYYY-MM-DD
   name: 김지완
   title: 포트폴리오 표지 제목
   intro: |
     JD와의 연결점을 짧게 서술 (2~4문장)
   cases:
     - id: <case-id>
       reason: "JD의 어느 항목에 대응하는지 한 줄"
   unmet:
     - "대응하는 사례가 없는 JD 항목"
   ```

7. **렌더링** — `python tools/build.py render <application-dir>`을 실행한다.
   `ready`가 아니거나 형식 검증에 실패한 사례가 섞여 있으면 스크립트가 멈추고
   이유를 출력한다 — 이 경우 해당 사례를 빼거나 먼저 `/review-case`를 거치게
   안내한다.

8. **미충족 요구사항 보고** — 렌더링이 끝나면 `unmet` 목록을 사용자에게 다시
   보여주며, 이것이 곧 면접 예상 질문이자 자기소개서 보완 지점이라는 것을
   알린다.
